В `pilot_timing.yaml` и `attribution.yaml` есть блок `launch` (`jobs: 16`, `shards`): общий запуск
`scripts/run_server.sh` (`cif.experiments.launch`) годится для E1 без изменений — проверено на `--smoke`-сетке
`pilot_timing.yaml` (`run`, 12 ячеек, 4 шарда, 0 ошибок) и `plan` для остальных. Шарды режутся как всегда:
шард `j` — `cells[j::S]`. `pilot_floor.yaml` **не менялся**: его хеш конфигурации (`9da2018d5f2c`) — хеш
зарегистрированного прогона, любая правка файла (даже блок `launch`) разорвала бы эту связь; при повторе
передайте `--jobs 16 --shards 16` в командной строке.

## Что изменили B1–B3 (кратко; полный текст — §12)

- **B1.** Единица работы вызова tabu — **чтения** (`num_reads`), каждое чтение — один простой поиск tabu
  (`num_restarts = 0`, детерминированный режим R12, длина поиска — по умолчанию `dwave-samplers`), tenure
  `max(5, ⌊N/4⌋)`: 5 при N = 16 и 6 при N = 24. Число чтений подбирает пилот на ≈ 1 с, как у SA и swap-SA.
  Старый режим (10 чтений, рестарты масштабируются) конфиги отвергают: у блока `pilot.work` и у сетки таймингов
  `num_restarts` обязан быть 0, `tenure` — по правилу.
- **B2.** Строка несёт `E_form_at_npipe_m = E_form(n_pipe(m))`, `E_prec_m = E_pipe(m) − E_form(n_pipe(m))` и
  `E_short_m = E_form(n_pipe(m)) − E_form(m) ≥ 0`, тождество `E_samp = E_prec + E_short`. Анализ: таблица
  `e_decomposition.csv`, доля ячеек с `n_pipe(m) < m` по конфигурации (то есть по сэмплеру), N, h и m, модели §7.3
  также для `asinh(E_prec/τ)` (файлы с меткой `prec_`).
- **B3.** «Настроенная конфигурация» — эталонная: SA — множитель штрафа 100, диапазон β `dwave`, 1000 развёрток;
  tabu — по B1, множитель 100; swap-SA — 200 развёрток, горячая температура по калибровке 80 % принятий,
  холодная `0.01·T_hot`; число чтений у всех — по пилоту на эталоне. Контраст сэмплеров — при эталонах;
  остальные уровни сетки описываются. **Exploratory:** уровень swap-SA `T_cold = 0.2·T_hot` (+1 600 ячеек) и
  любая конфигурация, выбранная после просмотра сетки (`models.chosen_after_grid`).

## Порядок работ

Обозначения: `<sha>` — короткий SHA коммита пакета; `OUT` — каталог результатов на сервере **вне** распакованного
пакета и вне репозитория. Запуск — `scripts/run_server.sh <config> …` (= `python -m cif.experiments.launch run
--config <config> …`, один поток на задание, `PYTHONNOUSERSITE=1`); приём — `cif.experiments.ingest` (регистрирует
прогон). Сервер gpu-07 общий (2 × Xeon Silver 4216, 32 физических ядра, 64 потока, governor `schedutil`, §12
2026-10-11): **не больше 16 одновременных заданий**, каждое привязано к физическому ядру (`--cores 0-31 --pin`);
нагрузка и governor пишутся в манифест. Пилот-тайминг и подтверждающая сетка идут с **одним и тем же числом
заданий (16)**: время вызова в строках тогда соответствует тому, под которое подбиралась работа. Launcher берёт
замок (`/tmp/cif_launch.lock`, или `$CIF_LAUNCH_LOCK`): на машине идёт одна стадия нашей работы за раз, E1 не
запускают одновременно со стадиями E2.

### 5. Приём пилота и отчёт (локально)

Каталог `$OUT/pilot_timing` копирует пользователь в `runs/incoming/E1-pilot_timing-<sha>/`. Затем:

```bash
D=runs/incoming/E1-pilot_timing-<sha>
python -m cif.experiments.ingest --config configs/E1/pilot_timing.yaml --shards $D/*_shard*.jsonl \
    --bundle-sha-file $D/BUNDLE_SHA --logs $D/launch_manifest.json $D/logs/*.log $D/env_*.json   # печатает: registered <run_id>
python -m cif.experiments.e1_pilot report --run runs/20261011-205903-E1-pilot_floor-9da201 \
    --run runs/<run_id_timing> --out results/E1/pilot/pilot_report.json
```

Код выхода `report`: 0 — отчёт годен для §12; 2 — записан, но не годен (список `PROBLEM:`); 1 — ошибка
(ячейки потеряны или с ошибкой). Отчёт содержит правило пола (`m0`, доли по N, h и m, интервалы Уилсона),
для каждого сэмплера и N — выбранную работу, медиану и квартили времени, `status` и всю кривую «работа —
время», эталонную конфигурацию (`reference`), окружение измерений (модель CPU, governor, нагрузка, процессы,
частота) и предупреждения.

Если `status` не `ok`:

- `edge_low` / `edge_high` — цель вне сетки: сдвиньте `start` / `ratio` / `count` (или `values`) в
  `pilot_timing.yaml` для этого сэмплера и N, закоммитьте, **перезапустите только часть 2** (в новый
  `--out-dir`);
- `off_target` — внутри сетки, но не ближе `tolerance`: сетка слишком грубая или измерение шумное
  (проверьте предупреждения о нагрузке и governor), уплотните сетку возле цели.

Прогон из `--smoke`, с грязного дерева или без одной из частей в отчёте не годен
(`valid_for_section_12: false`); значения из такого отчёта не принимает ни `make-config`, ни `cells()`
подтверждающего конфига.

### 6. Значения пилота — в §12 и в конфиг

Оркестратор записывает в §12 до первого подтверждающего прогона: работу вызова по сэмплерам и N (для tabu —
число чтений при `num_restarts = 0`), `target_s`, `run_id` частей, SHA отчёта, `W = 16` и модель сервера (`m₀ = 1`
уже записано). Годный отчёт содержит готовую запись в формате §12 (поле `section_12` в JSON, её же печатает
`report`): в ней `<дата>` и `<кто согласовал>` — заглушки. Затем:

```bash
python -m cif.experiments.e1_pilot make-config --report results/E1/pilot/pilot_report.json --config configs/E1/attribution.yaml
python -m cif.experiments.run --config configs/E1/attribution.yaml --dry-run     # 27200 cells
git add configs/E1/attribution.yaml results/E1/pilot/pilot_report.json && git commit -m "E1: значения пилота в конфиге"
```

`make-config` переписывает только блок между `# >>> pilot` и `# <<< pilot` (значения и происхождение:
`run_id`, SHA отчёта), проверяет, что получившаяся сетка допустима, и только потом пишет файл. Блок содержит
`m0` из прогона floor (= 1, и он совпадает с `h1a.m0` в `analysis.yaml`: расхождение анализ отвергает).

### 7. Подтверждающая сетка: 27 200 ячеек, 16 шардов по 5 пар, 16 заданий

Новый пакет из нового коммита (п. 1), на сервере п. 2, затем (прогон на тестовых сидах требует `BUNDLE_SHA`):

```bash
python -m cif.experiments.launch plan --config configs/E1/attribution.yaml --cores 0-31 --pin --out-dir $OUT/attribution
scripts/run_server.sh configs/E1/attribution.yaml --cores 0-31 --pin --out-dir $OUT/attribution
python -m cif.experiments.launch status --config configs/E1/attribution.yaml --out-dir $OUT/attribution   # 27200/27200
grep -l '"error"' $OUT/attribution/*_shard*.jsonl                          # ничего
PYTHONPATH=src python -m cif.experiments.e1_pilot env > $OUT/env_end.json
```

**16 шардов (`launch.shards`) делят 80 пар** (`cell_order: interleaved`): шард содержит целые пары, и оракул
инстанса (сертифицированный оптимум SCIP, перебор всех K-подмножеств, доводка 200 лучших) считается один раз на
шард. Число шардов задано в конфиге (`launch.shards: 16`); другое `--shards` корректно, но пересчитывает оракул
в нескольких шардах (умолчание launcher без `launch.shards` — `8·jobs = 128` шардов, 5 пар не делятся). Один
процесс на шард (`--workers 1`) launcher обеспечивает сам.
Прогресс — `status`. Перезапуск — та же команда.

### 8. Приём и анализ (локально)

Приём тоже с чистого дерева на том же коммите: манифест принятого прогона берёт `git_dirty` с машины, где
идёт `ingest`, а анализ помечает прогон с `git_dirty != false` как неподтверждающий.

```bash
D=runs/incoming/E1-attribution-<sha>
python -m cif.experiments.ingest --config configs/E1/attribution.yaml --shards $D/*_shard*.jsonl \
    --bundle-sha-file $D/BUNDLE_SHA --logs $D/launch_manifest.json $D/logs/*.log $D/env_*.json
python -m cif.experiments.e1_analysis --run runs/<run_id> --config configs/E1/analysis.yaml \
    --out results/E1/analysis/<run_id> [--h1c-p <p>]
```

`--h1c-p` — одностороннее p-значение H1c из анализа E2 (Холм по `{H1a, H1c}`, §7.1); без него H1a решается,
только если `2p ≤ α` (подтверждена) или `p > α` (не подтверждена), иначе `pending_h1c`. Анализ ~10 минут (оценка,
см. ниже). Результаты:

- `h1a.json` — тест, Холм, исход, размер эффекта с бутстрап-ДИ (подтверждающий; `m₀ = 1`);
- `shares_e_form.csv`, `e_form.csv`, `e_form_difference.csv` — оценки потолка (доли с Уилсоном при m ∈ {1, 50});
- `e_samp.csv`, `e_decomposition.csv` — остаток сэмплера по конфигурациям: `e_samp.csv` — медианы по сидам
  инстанса (§7.2); `e_decomposition.csv` — **тождество** `E_samp = E_prec + E_short` на средних по сидам
  (в нём тождество линейно; медиана суммы не сумма медиан) и **доля ячеек с `n_pipe(m) < m`** по конфигурации (то
  есть по сэмплеру), m, N и h (колонки `share_short`, `n_pipe_median`);
- `pool_curve.csv`, `sampler_diagnostics.csv` (время вызова, доля допустимых, τ Кендалла, разнообразие пула),
  `design.csv` (доля связывающих, глубина `s_cont/K`, CV волатильностей по h);
- `fixed_effects_*.csv`, `predictions_*.csv`, `contrasts_*.csv`, `models_*.json` — модели §7.3 для
  `asinh(E_samp/τ)` (без метки) и для `asinh(E_prec/τ)` (метка `prec_`);
- `diagnostics.json`, `analysis_manifest.json` (SHA-256 файлов, версии, предупреждения, роль каждой конфигурации
  в `configurations`; `confirmatory: true` только для прогона на тестовых сидах из чистого дерева;
  `output_status` — статус каждого файла по плану: подтверждающий только `h1a.json`, оценки, описательные
  таблицы и **exploratory** — модели и контрасты §7.3, правило §9).

**Роли конфигураций (`role` в таблицах по конфигурациям, предсказаниях и контрастах).** `reference` — эталон (B3);
`grid` — остальные уровни вложенной сетки плана (описываются); `exploratory` — уровень swap-SA `T_cold = 0.2·T_hot`
и всё, что аналитик перечислил в `models.chosen_after_grid` после просмотра сетки. Контраст между сэмплерами
(`contrasts_*.csv`) считается для каждой пары конфигураций: `role = reference` — при эталонах (**это контраст
плана**), `exploratory` — если хотя бы одна сторона exploratory, `grid` — описательно по остальным уровням.
Уровни swap-SA, которых нет в плане, — отдельные модели (`swap_sa[cold_ratio=0.2]`, `exploratory: true` в
`fixed_effects_*.csv`), чтобы модель плана была моделью строк плана и только их.

## Оценки времени (оценки, не замеры подтверждающего прогона)

версионируется, числа ниже — округлённые): время вызова `t ≈ a + b·чтения`.

| Сэмплер (эталон), N | a, с | b, мс/чтение | 1 с ≈ чтений |
|---|---|---|---|
| SA, штраф 100, β `dwave` (1000 развёрток), 16 / 24 | 0 | 0.43 / 0.91 | 2300 / 1100 |
| SA, β по масштабу цели (на той же работе) | 0 | 0.010 / 0.016 | — (0.02–0.03 с на работе SA) |
| tabu, штраф 100, `num_restarts = 0`, 16 / 24 | 0 / 0.06 | 2.8 / 2.0 | 350 / 480 |
| swap-SA, `T_cold = 0.01·T_hot` (200 развёрток), 16 / 24 | 0.15 | 0.42 / 0.86 | 2000 / 990 |
| swap-SA, `T_cold = 0.2·T_hot` (та же работа) | 0.15 | 0.56 / 1.17 | ≈ 1.3 с на работе эталона |

| Часть | CPU-часы (оценка) | при 16 заданиях (оценка) |
|---|---|---|

| Подтверждающая сетка | ≈ 6.5 (5–9): 5.5 вызовы сэмплеров (≈ 12.5 с на инстанс и сид: 5 SA(β `dwave`) + 5 tabu + swap-SA 1 + 1.3 с, SA(β по цели) 0.1 с), ≈ 0.4 доводка новых подмножеств пулов (N = 24: до 2.3 мс на доводку), ≈ 0.1 оракулы (0.8–1.8 с при N = 16, 2.0–2.7 с при N = 24) | 30–45 мин |

Скорость ядра gpu-07 неизвестна: её надо умножить на отношение скоростей к ноутбуку. Сетки таймингов рассчитаны на
разброс в 2–3 раза в обе стороны (медиана вызова 1 с при N = 24 для swap-SA — 990 чтений в сетке 300…7600; для SA —
1100 в сетке 250…6400; для tabu — 480 в сетке 60…1900). Если машина медленнее ноутбука более чем в 3–4 раза,
отчёт скажет `edge_low` для swap-SA или SA при N = 24: сдвиньте `start` и перезапустите часть 2. План (§8)
оценивает E1 в 40–80 CPU-ч: для RQ1 это завышено примерно на порядок.

## Решения при неоднозначностях плана (для §12 / отчёта оркестратору)

1. **«Настроенная конфигурация» (§6, §7.3).** Прочитана по B3 как эталонная: `REFERENCE` в `e1_attribution.py`
   (SA — штраф 100 и β `dwave`; tabu — штраф 100; swap-SA — `T_cold = 0.01·T_hot`). Работа подбирается на эталоне:
   `_reference` в `e1_pilot.py` отвергает другую эталонную конфигурацию в `pilot_timing.yaml`; `models.reference`
   в `analysis.yaml` анализ тоже отвергает, если оно не эталон плана (иначе «выбор после просмотра сетки»
   выглядел бы как предрегистрированный контраст). Конфигурацию «после сетки» записывают в
   `models.chosen_after_grid`: она получает `role = exploratory` во всех таблицах. Подтверждающая сетка (тестовые
   сиды) обязана содержать эталон каждого сэмплера: `cells()` отвергает сетку без него.
2. **Что масштабируется.** План называет «чтения × развёртки» (SA, swap-SA) и «рестарты» (tabu); B1 уточняет
   «рестарты у tabu» как «независимые поиски»: масштабируется число **чтений** у всех трёх, остальное — эталон. SA:
   1000 развёрток (dwave); swap-SA: 200 развёрток; tabu: простой поиск на чтение (`num_restarts = 0`),
   `tenure = max(5, N // 4)`. Размер пула — число чтений, поэтому пул вызова ограничен сэмплером, а не константой
   реализации. **Замеры рецензента** (16 инстансов, сиды вне плана): пул tabu при чтениях как единице работы 5–13,
   у swap-SA с эталонным расписанием 1–11, у SA ≥ 200; поэтому `E_samp(m)` при больших m измеряет в основном
   размер пула, и B2 отделяет этот вклад (`E_short`) от точности сэмплера (`E_prec`).
3. **Время вызова** — `solve_s` вызова сэмплера (то же поле пишет подтверждающая сетка), без `build_s`. Для
   swap-SA оно включает калибровку горячей температуры (микросекунды) и не зависит от того, какой `cold_ratio`
   у ячейки, кроме скорости самого отжига: при `T_cold = 0.2·T_hot` принимается больше обменов, вызов на ≈ 30 %
   дольше при той же работе. Статистика: медиана по инстансам (20 пар × 2 уровня на N) от медианы по 3 повторам;
   критерий — ближайшее к 1 с на логарифмической шкале, при равенстве меньшая работа; `tolerance 0.2` — только для
   статуса.
4. **Правило пола.** Доля по всем 80 инстансам (оба N, оба уровня h), сравнение `≥ 20 %` точное (дробью), `>`
   строгое. Один `m₀` на дизайн; доли по N, h и m — описательно. Результат записан в §12: `m₀ = 1`. Значение
   `m₀` лежит и в блоке `pilot` конфига подтверждающего прогона, и в `h1a.m0` файла `analysis.yaml`; анализ
   берёт блок прогона, а при расхождении с `h1a.m0` отказывает.
5. **Тестовые сиды RQ1.** План даёт диапазон 2000–2999 и «40 сидов на N», но не номера: принято подряд, как
   у калибровки: N = 16 — 2000–2039, N = 24 — 2040–2079; сиды решателя 20000–20009.
6. **H1a.** Односторонний (больше) знаковых рангов Уилкоксона, ранги внутри страт N, нулевые разности
   отбрасываются (`zero_tol = 1e-8` в единицах `s*`: ниже точности доводки), ничьи — средние ранги. p-значение
   *точное* по перестановке знаков при данных рангах (ДП по удвоенным рангам); нормальное приближение с
   поправкой на ничьи — для сверки со scipy.
7. **Единица в моделях §7.3.** План: отклик `asinh(E_samp(m)/τ)`; §7.2: сводка по инстансу — медиана по сидам.
   Основная единица — медиана по сидам инстанса и конфигурации; строки отдельных сидов — проверка
   (`models.units`). Случайный эффект — только свободный член инстанса, как в плане: зависимость пяти размеров
   пула одного вызова и эффект «инстанс × конфигурация» в модели не учтены. По B2 те же модели строятся для
   `asinh(E_prec(m)/τ)` (`models.responses`); тестов нет.
8. **Единица тождества B2.** `E_samp = E_prec + E_short` линейно по ячейкам; в таблице `e_decomposition.csv` это
   средние по сидам инстанса и затем по инстансам (бутстрап на тех же перевыборках, поэтому средние складываются в
   каждой перевыборке, и `identity_gap` равен ошибке округления). Медианы по сидам (`e_samp.csv`, модели) тождеству
   не подчиняются, и их части не складывать. Ячейка без допустимого подмножества (пустой пул) считается
   «короткой» при любом m в доле `share_short`, а `E_prec` и `E_short` у неё не определены.
9. **Доля коротких пулов.** `n_pipe(m) < n_form(m)`; в дизайне `C(N, K) ≥ 560 > 200`, поэтому `n_form(m) = m` и это
   `n_pipe(m) < m`, как в B2. Доля — среднее по инстансам доли сидов инстанса (при 10 сидах на инстанс это доля
   ячеек), интервал — бутстрап по парам внутри N (а не Уилсон по ячейкам: ячейки одного инстанса зависимы).
10. **Бутстрап-ДИ.** Процентильные, 95 %, кластер — пара (оба уровня h), страта — N; сид и размер в
    `analysis.yaml`, поток каждой ячейки таблицы — `SeedSequence([seed, таблица, индексы])`.
11. **Сид сэмплера.** `SeedSequence([solver_seed, pair_seed, n, h, сэмплер, штраф, β, cold_ratio])`; `cold_ratio`
    входит только у swap-SA, поэтому SA и tabu сохраняют прежние потоки, а два уровня swap-SA одного инстанса и
    сида не делят поток (§3). Горячая температура swap-SA калибруется внутри вызова на том же потоке, поэтому
    у двух уровней она может отличаться в пределах шума калибровки.
